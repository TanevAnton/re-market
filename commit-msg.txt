fix: `required` was decorative on listing-scoped specs

The wizard validated its scalar fields and left the spec blob alone, so
three specs were marked required and nothing enforced them anywhere:
monitor.dead_pixels, prebuilt.cpu_model, prebuilt.gpu_model. A flag that
reads as a guarantee and is not one is worse than no flag — it tells the
next person the question is already handled.

TWO THINGS HAD TO BE TRUE FIRST.

**Every required spec must be answerable honestly**, or the field
collects guesses, which is worse data than a blank. dead_pixels offers
„Не е проверено"; a seller listing a whole machine knows what is inside
it, and for `prebuilt` those two fields ARE the specification, because
that category has no catalogue row behind it — without them the listing
is „компютър, 1200 лв", which is the OLX listing this site exists not to
be. A test asserts that property for every category, so adding a
`required` flag to something unanswerable fails rather than ships.

**The fields had to leave „Подробности по желание".** Validating them
where they were would reject a listing over a field inside a collapsed
panel headed „by choice" — one the seller cannot see and was told was
optional. Required specs now render in the body of step 3; the rest stay
in the panel. The input markup moved to partials/spec-field.blade.php so
the two places cannot drift.

**Enforced on the edit screen too.** Doing it only on the way in is the
same hole with an extra step: publish with the field filled, then blank
it afterwards. One `RequiredSpecs` class, both screens — the same reason
the offer floor lives in the service rather than in each caller.

A required <select> loses its blank option, because the schema already
provides the honest way out and an empty choice would only be a way to
skip the question. Messages name the field as rendered rather than the
column: „Попълни „Дефектни пиксели"", not „specs.dead_pixels".

10 tests, 36 assertions.
